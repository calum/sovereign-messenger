PROJECT: Sovereign Mesh (sovereign-messenger)
STATUS: experimental, not audited, not for sensitive use yet.
PURPOSE: P2P messenger for a closed group (up to 5 people) on Android. No servers, no cloud, no disk storage of messages. Post-quantum key exchange.
EXPERIMENT: tests whether a fully AI-generated P2P messenger can be made private and secure. None of the code is human-written. Humans test it, and their results decide what is working.

COMPONENTS
- rust-core/  Rust library (crate: rust-core)
  - secret.rs     SecretBytes (mlock + zeroize), Key32 (zeroize on drop)
  - handshake.rs  X25519 + ML-KEM-768 hybrid key agreement plus static-static DH (HKDF-SHA256 root key); responder checks the initiator against its pin
  - ratchet.rs    symmetric chain, ChaCha20-Poly1305, bounded skipped-key cache (out-of-order), replay rejected
  - double_ratchet.rs  DH ratchet over the chains: X25519 key in each header, HKDF-SHA256 root, versioned header
  - update.rs     Ed25519 verification of update payloads against a pinned key
  - store.rs      RAM-only chat store, no persistence API
  - error.rs      CoreError (no secret content in messages)
  - ffi.rs        UniFFI facade: Messenger object, the only surface Kotlin calls
  - transport.rs  Transport trait; TcpTransport (length-prefixed frames, 64 KiB cap)
  - wire.rs       handshake and ratchet frame layout; send and receive helpers
  - pairing.rs    QR payload v2 (identity keys and onion key), fingerprint, two-part split
  - vault.rs      encrypted identity vault: identity secrets and pins sealed under a data key (ChaCha20-Poly1305)
  - onion.rs      v3 onion address encode and parse, checked against arti's addresses
  - tor.rs        Tor carrier (cargo feature `tor`, arti 0.47 pinned): framing over an onion stream and TorNode, whose service key is held in memory only
  - apk_transfer.rs  APK transfer over local Wi-Fi
  - scripts/      build-android.sh (NDK cross-compile), gen-kotlin.sh (bindings)
- app/           Android app, Kotlin + Jetpack Compose, minSdk 29, targetSdk 35, package org.sovereign.mesh
  - MainActivity: FLAG_SECURE, wipes core on stop
  - core/CoreBridge: forwards to generated UniFFI bindings (uniffi/rust_core); connect, listen, send, receive over TCP, plus Tor calls
  - core/IdentityVault, AndroidKeystoreWrapper: store the sealed identity; the Keystore wraps the data key
  - core/TorController, TorUi: start Tor, show its status, accept calls, decide when to dial
  - ui/: TourScreen, ChatListScreen, ChatScreen (connect or wait for contact, send, receive loop)

NOT DONE
- Tor between two phones, and Tor on Android at all: not run. No claim of privacy from a network observer until PLAN.md T4 passes
- any transport between two phones: not run
- the Keystore vault, camera scanner and chat screen on a device: not checked
- handshake authentication of the initiator: done via static-static DH and the responder's pin (PLAN.md Decisions, 2026-10-24); not independently reviewed; no key-confirmation message; both phones must scan each other's QR first
- QR onboarding camera scan on a device, APK transfer between phones, signed-update delivery: not verified or not started
- ratchet DH step (post-compromise security): implemented in double_ratchet.rs; standard construction, tested in Rust, not independently reviewed; limits in PLAN.md Decisions (2026-10-24)

CONSTRAINTS FOR CHANGES
- never write messages to disk; the identity and pinned contacts only as the encrypted vault; Tor's public cache only under filesDir/tor (CLAUDE.md rule 1)
- zeroize every type that holds secrets
- no plaintext in logs or errors
- keep allowBackup=false and FLAG_SECURE
- use existing RustCrypto crates; do not invent primitives
