## Decisions

- **2026-10-24, identity lifetime:** the identity is generated when the process starts (`SovereignApp` creates `CoreBridge`, which creates `Messenger`) and is never written to disk. Closing the app discards it, so every contact must scan a new QR code after a cold start. Cost if wrong: more pairing for the user; the key is not stored anywhere, so storage cannot leak it.
- **2026-10-24, QR payload format v1:** magic `SMQR`, version byte `1`, X25519 public key (32 bytes), ML-KEM-768 encapsulation key (1184 bytes), one length byte, then a connection hint of up to 64 printable ASCII characters. Rust builds and parses the bytes (`rust-core/src/pairing.rs`); Kotlin maps each byte to one ISO-8859-1 character, encodes byte mode with error correction L, and does not interpret the payload. - **2026-10-24, static-static DH authenticates the initiator:** Ruling: the handshake adds a third DH, between the initiator's long-term X25519 key and the responder's long-term X25519 key, to the HKDF input that already holds the ephemeral DH and the ML-KEM secret. The initiator puts its static public key in the handshake frame, so the frame layout changes; the QR payload stays v1. The responder compares that key with the X25519 key pinned for the peer's label before any decapsulation, and refuses a mismatch with `CoreError::Auth`, which holds no key. Why: the project owner ruled for it. It uses only the X25519 and HKDF crates already in the tree, and it needs no signature primitive. Cost if wrong: the design is not independently reviewed, and it has not been checked against a formal model. Each phone must scan the other's QR code before a session can open, which the UI does not yet guide the user through. The handshake has no key-confirmation message, so a responder with the wrong key is found only when the first chat message fails to open. A captured handshake frame can be replayed to a listener. That cannot forge or read messages, but it can replace the listener's session; freshness is not tracked, and this is not fixed. A low-order pinned key gives an all-zero static DH term. The check `was_contributory` is not used here, and the ephemeral DH already skipped it.
- **2026-10-24, the send counter commits after the write:** Ruling: `Chain::seal_with` builds the message and the next chain key, passes the message to the transport, and advances the counter and chain key only if the transport returns `Ok`. A failed write leaves the chain where it was, so the next successful send carries the counter the receiver expects. The receiver is unchanged: it advances only after a successful open. Why: the receiver cannot tell a lost frame from a skipped counter, so the sender must never skip one. Cost if wrong: a write that fails after part of a frame reached the socket leaves the byte stream corrupt. `TcpTransport` does not mark the link dead, so a session should be re-handshaken after any send error. - **2026-10-24, skipped-key cache size:** `MAX_SKIP` is 100 counters per receive and `MAX_CACHED_KEYS` is 100 keys per cache (`rust-core/src/ratchet.rs`). A full cache holds 3.2 KB of key material. The numbers are a choice, not a standard value. Cost if wrong: a burst of more than 100 lost messages cannot be read later; a larger cap holds more keys in RAM.
- **2026-10-24, ratchet frame v1 layout:** `[tag 0x02][version 0x01][ratchet X25519 public key, 32 bytes][pn, u64 big-endian][n, u64 big-endian][ciphertext]`. The old 9-byte header (tag and counter) is gone. The Kotlin `WireMessage` record gained `ratchetPublic` and `previousCount`, so the app and core must be built from the same commit. Cost if wrong: a frame with another version byte is refused, not misread.
- **2026-10-24, DH ratchet design (not independently reviewed):** the standard Double Ratchet construction, with one deviation. Both sides start from the handshake root with the same chain labels as before, because there is no prekey to start a DH step, so each side can send before it has a peer key. The first key seen from the peer is accepted without a DH step; a message that does not authenticate on the handshake chain is tried as a DH step, and state changes only after authentication. A side makes a new ratchet key on its next send after receiving a new peer key. Root KDF: HKDF-SHA256, salt = root key, input = the DH output, info `sovereign-p2p v1 dh ratchet`, 64 bytes split into a new root key and a chain key. Message keys use the chain KDF already in use. Limits: (a) SUPERSEDED 2026-10-29: crossing first steps are prevented by role-based stepping (see the 2026-10-29 ratchet entry); (b) a handshake-chain message delayed past the peer's first DH step is refused; (c) a skipped key is kept for the previous epoch until it is used or evicted. Why: the owner asked for the standard construction on existing crates. `Chain` (symmetric, no DH step) is no longer on the wire path. Cost if wrong: a flaw in the construction breaks recovery or confidentiality without a visible error, so it must be reviewed before anyone relies on it (section 6).

- **2026-10-24, QR pairing payload is split across two codes (plan A2, wire change):** a 1.2 KB payload as one code is version 27, and ZXing 3.5.4 failed to decode about 7% of such codes (15/200 in the reproduction above). Reassembly (`rust-core/src/pairing.rs`, `Assembler`) refuses a missing, duplicated, out-of-range or mismatched part, and refuses a complete set whose joined bytes do not match the id, so a tampered part cannot pin. The payload inside the parts is the unchanged v1 layout, so `decode` and its version check are the same. A single v1 code is refused, not misread. Splitting alone did not fix it: with two codes the 200-payload test still failed 22 of 200. Measured by experiment, the failures are specific symbols that ZXing's detector rejects at their smallest version; they do not depend on size, scale, quiet zone, binarizer or error level, and a one-version larger symbol decoded 23 of 24 of them (two versions, the last one). The cause inside ZXing is not identified. So `QrCodec.encode` reads each code back with the scanner's reader and moves up to three versions larger when it does not read back. The bytes do not change. The Android `.so` files were rebuilt with `rust-core/scripts/build-android.sh`. Cost: two scans per pairing, and a few codes are larger than the smallest version. The test `twoHundredFreshPayloadsDecodeEveryTime` is re-enabled and passes with 0 failures over 200 fresh payloads on the JVM. It does not show that a camera will decode the code. A2 is therefore MITIGATED on clean renders, not resolved. The root cause in ZXing is unknown, and the camera path is untested. Not verified on a phone: the camera path, the scanner's collection of two codes, and reading between two phones have not been run. The id is an integrity check, not authentication; the fingerprint comparison in person is still the trust step. Cost if wrong: a code that the scanner reads on the JVM may still fail through a camera, and the on-screen pair is untested on a device.
- **2026-10-24, handshake replay is refused by a challenge and a confirmation tag (plan A5, wire change):** Ruling: the responder sends a fresh random 32-byte challenge before the initiator's handshake, once per connection. The initiator binds the challenge into the root key (HKDF input, under its own label) and sends a 32-byte key-confirmation tag: HMAC-SHA256 keyed with the root, over the label "sovereign-p2p v1 key confirmation", the ephemeral key, the initiator's static key, the ML-KEM ciphertext and the challenge. The responder checks the tag with a constant-time comparison before it returns a root, so a refused handshake stores no session. Why: a captured handshake could be replayed to a listener that already had a session with the same peer, which replaced the live session. A replay could not forge or read messages, but it broke the live session. Wire change: new frame tag 0x03 carries the challenge (33 bytes: the tag and 32 bytes). The handshake frame is now 1185 bytes; the 1153 in the frame cap entry above is the size before this change. The handshake ends with the 32-byte tag, and TAG_HANDSHAKE is unchanged. The in-process API changed: `responder_challenge` issues the challenge; `start_session` and `accept_session` take it. `accept_session` spends the stored challenge on every attempt, so a challenge cannot authenticate a second handshake. The facade keeps one pending challenge, so a second `responder_challenge` call replaces the first. Network path: `connect_peer` receives the challenge before it initiates, and `accept_one` sends a fresh one before it reads the handshake. - **2026-10-29, ratchet role-based stepping (owner approved; not independently reviewed):** Ruling: `DoubleRatchet::new` takes a `Role` (initiator or responder, matching the handshake).
