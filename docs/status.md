# Detailed status

The long version of where the project stands, moved out of the README to keep it short. [PLAN.md](../PLAN.md) is the checklist and the decisions log; [owner-test-list.md](owner-test-list.md) lists the checks that need a person and hardware.

Be skeptical of every claim here until it has been tested and reviewed.

## What works today

- **`rust-core/`**: a Rust library with
  - a memory layer that zeroizes secrets on drop and tries to `mlock` them,
  - a hybrid key exchange, X25519 + ML-KEM-768 (FIPS 203), plus a static-static X25519 DH that makes the responder check the initiator against its pin; all three feed one HKDF,
  - a Double Ratchet (ChaCha20-Poly1305, X25519 DH steps, HKDF-SHA256 root key) that rejects tampered and replayed messages and accepts out-of-order ones within a bounded skip. DH steps are role-based: only the handshake initiator takes the first step, so the two sides cannot step at the same time,
  - Ed25519 verification of update payloads against a developer key compiled into the app (not set yet, see below), and a version rule that refuses equal or older builds,
  - a RAM-only chat store with no persistence API.
  - a UniFFI facade (`ffi.rs`) that exposes a `Messenger` object; keys and plaintext stay in Rust.
  - a framed transport trait with a TCP implementation (64 KiB frame cap, refused oversize and truncated frames),
  - a liveness check on every session: while a link is idle each side sends a small authenticated ping (envelope kind `0x13`, never stored or shown) after 25 s of silence, and a session that has received nothing for 75 s, or that fails to open 5 frames in a row, is declared dead and its link is closed, so the app redials with a new handshake,
  - an encrypted identity vault: the long-term identity and pinned contacts are sealed (ChaCha20-Poly1305) under a data key that the Android Keystore wraps; messages and sessions are never stored,
  - a stable v3 onion address per identity, carried in the QR code (payload version 2), and a Tor transport (cargo feature `tor`, using arti 0.47 pinned) that hosts the identity's onion service with its key held only in memory. The same framing rules apply over an onion stream as over TCP.
  Pairing (QR payload built in Rust, TOFU pin, refused changed key), the transport, the handshake, the ratchet, the vault, the update check and the liveness check each have unit and integration tests in `rust-core/`. Counts are not listed here because they go stale; the `mise` tasks are the source of truth for running them (`mise run rust:test`). CI (`.github/workflows/ci.yml`, added 2026-10-29) runs the Rust checks, with and without the Tor feature, on every push and pull request. It has not been seen running on GitHub yet. CI does not build the Android app or run the Kotlin tests.
- **`app/`**: an Android (Kotlin, Jetpack Compose) shell with a three-card tour, a contact list with last message, unread count and online state, a chat screen with message bubbles, sender names, times and sent/delivered/read marks, a guided add-contact flow, a settings screen, working system back navigation, `FLAG_SECURE` on every window, and backups disabled in the manifest. `CoreBridge` calls the generated UniFFI bindings for `rust-core` (arm64-v8a and x86_64 libraries are built by `rust-core/scripts/build-android.sh`). JVM tests in `app/src/test` run the real core through JNA, including a QR encode and decode round trip and a loopback message over TCP (`mise run check` runs them). They need the Android SDK and are not run in CI. An Updates screen (opened from Settings, "App updates") can receive an APK from another phone over local Wi-Fi, check its signature in the core and hand it to the system installer, and can send an APK with its signature file to another phone. Identity deletion is in Settings ("Delete my identity").

## What does not work yet

- Nothing has been sent between two phones, over Tor or over TCP. The QR code now carries the contact's onion address; the same-Wi-Fi TCP test path still needs a typed `host:port`.
- Tor has run over the real network only in the core's live test on a laptop (two identities in one process). It has not run between two machines, from the app, or on a phone. The first publish of an onion service has taken from 18 seconds to about 5 minutes; a start with saved state took 20 seconds against 88 cold. Chats stay in memory while the app process lives (owner decision, 2026-10-29), so a quick app switch no longer costs a reconnect; if Android stops the process, chats are lost and reconnecting can take minutes.
- The initiator is authenticated by the responder's pin (static-static DH, PLAN.md, Decisions, 2026-10-24). Both phones must scan each other's QR code first. This is tested in Rust but not independently reviewed. The responder sends a fresh challenge and the initiator proves it with a confirmation tag, so a captured handshake does not replace a live session. The challenge carries a one-use responder ephemeral key (handshake v2), so a later theft of the responder's long-term keys does not open recorded handshakes.
- The app has been installed and started on one phone (owner report). The camera scanner, the Keystore vault, Tor on Android and the chat screen have not been checked there.
- Updates: the Updates screen, the APK transfer and the signature check exist, but `DEVELOPER_PUBLIC_KEY` in `rust-core/src/update.rs` is `None`, so every update is refused and nothing can install. The transfer has not run between two phones. The QR code carries the identity keys and onion address, not a handshake ephemeral key (each handshake makes its own; see PLAN section 2).
- The DH ratchet step is the standard Double Ratchet construction, tested in Rust, but it has not been independently reviewed. Only the handshake initiator takes the first DH step, so the two sides can no longer step at the same time (this assumes each link delivers in order, which TCP and Tor streams do). The remaining limit is narrow: a message the responder sent on the handshake chain that is overtaken by the initiator's first DH step is refused. The cost of the rule is that the responder's first DH recovery waits one extra round trip (role-based stepping, PLAN.md Decisions 2026-10-29). If the ratchets ever do fall out of step, five failed frames in a row end the session and the app redials, instead of showing a dead link as live.
- Nothing here has been independently reviewed. The cryptography uses third-party crates (`ml-kem`, `x25519-dalek`, `ed25519-dalek`, `chacha20poly1305`, `hkdf`) that have not been audited as part of this project.

## Security status

| Property | Status |
|---|---|
| Post-quantum key exchange | Implemented in the handshake (ML-KEM-768 + X25519). Used in the live Tor test on a laptop; not yet between phones. |
| Initiator authentication | Implemented: static-static DH and a pin check in the responder. Low-order X25519 keys are refused in the handshake and in the QR decode (2026-10-29). Tested; not independently reviewed. |
| Forward secrecy of the handshake against later key compromise | Implemented (handshake v2, 2026-10-29): the responder sends a fresh ephemeral X25519 key with each challenge and the root includes `DH(initiator ephemeral, responder ephemeral)`. With the responder's long-term X25519 and ML-KEM keys and the recorded transcript, the root of a recorded session cannot be recomputed (unit test). Holds only while the ephemeral secrets are gone; the responder zeroizes its secret when the handshake is processed or the challenge is replaced, but copies on the stack are not all wiped. Old builds cannot connect to v2 builds. Tested; not independently reviewed. |
| Forward secrecy within a chain | Implemented (symmetric ratchet). |
| Post-compromise security | Implemented (DH ratchet step, role-based so steps alternate). The responder's first recovery waits one extra round trip. Tested; not independently reviewed. |
| Dead or half-open links | Handled in the core (2026-10-29): ping after 25 s idle, session declared dead after 75 s of silence or 5 failed opens in a row, link closed, app redials. Tested in Rust; not seen over a real Tor circuit or on a phone. A Tor-level observer sees a small frame about every 25 s per direction while a link is idle and the app is online; this is a fingerprint of an idle link and wakes the radio. |
| Metadata resistance / onion routing | Written, not proven. Each identity has a stable v3 onion address (in the QR code), the core hosts the onion service with the key held only in memory, and contacts dial each other over Tor. Unit tests cover framing, the in-memory key and the dial/wait rule. In one live test on a laptop (two identities in one process) it connected over the real Tor network and exchanged messages; it has not run from the app, on a phone, or between two machines, so no privacy claim is made. The same-Wi-Fi TCP path is a test path and reveals addresses on the local network. |
| RAM-only messages | Enforced in the Rust store (no persistence API). The Android app does not write message data to disk, but this is not yet verified. |
| Stored identity and contacts | Implemented, not run on a device. The identity secrets and pinned contacts are sealed by the Rust core (ChaCha20-Poly1305) under a data key that the Android Keystore wraps; app-private files, excluded from backup. Messages and sessions are never stored. Tested on the JVM with an in-memory stand-in for the Keystore; the real Keystore path (including StrongBox) has not run. Deleting the identity (Settings, "Delete my identity") stops Tor and the connections, deletes Tor's folder, wipes the old core's chats and sessions and releases it, deletes the vault even if an earlier step failed, then starts a new identity. There is no recovery. If starting the new identity fails, the app keeps pointing at the released core until the next launch, which starts clean. Not run on a device. |
| Memory locking (`mlock`) | Best effort. Can fail under a low `RLIMIT_MEMLOCK`; the code records the failure instead of hiding it. Secrets are zeroized on drop but never `munlock`ed (locked pages stay locked until exit, so a drop cannot unlock a neighbour's page; hardening review F2, closed). Not run on Android. Copies made on the stack during crypto operations are not all wiped. |
| Screenshot / recents protection | `FLAG_SECURE` set in `MainActivity`. Not verified on a device. |
| Crash reporting | An uncaught Kotlin error opens a report screen (error class, causes, stack, phone model; the exception message is printed only for the core's fixed-string errors and a short list of framework errors, so user text cannot end up in it) with Copy and Share, in its own process, held in memory only and never written to disk. A native crash is read back from Android's exit history on the next start (last 10 minutes only). The formatter has JVM tests; the screens, the handler and the exit-history path have not run on a device or been compiled in this change. A native crash gives only a signal and description, not a stack. |
| Cloud/device backups | Disabled in the manifest and backup rules. |
| Signed updates | Signature and version check implemented in Rust, with a delivery path (Updates screen, APK transfer over local Wi-Fi, system installer). No developer key is compiled in (`DEVELOPER_PUBLIC_KEY` is `None`), so every update is refused today. The transfer has a 10-minute overall deadline. Not run between phones. |

## Known limits from the 2026-10-29 review

A full code review of main (`d822ed2`) produced the findings below. The fixes are listed in [review-fix-plan.md](review-fix-plan.md) and in PLAN.md Decisions (2026-10-29). These are the limits that remain:

- **Pairing connects before fingerprints are compared (finding 2.7, owner accepted).** Scanning a code pins the contact, and the app starts dialling or accepting that contact within seconds, before the two people have compared fingerprints. The comparison is still the trust step; if the fingerprints differ, remove the contact. A change to hold the connection until confirmation was proposed and dropped by the owner.
- **A stalled write can delay one peer's incoming frames (finding 2.9, accepted).** The session's ratchet lock is held while a frame is written, so a receive from that same peer can wait up to the write timeout (60 s over Tor, 10 s over TCP). Other peers are not affected. A fix needs a send/commit split in the ratchet and was declined (PLAN.md Decisions, 2026-10-29).
- **Handshake-chain messages overtaken by the initiator's first DH step are refused** (see the ratchet limit above).
- **Old and new builds do not interoperate.** The handshake v2 challenge frame is 65 bytes, so builds from before 2026-10-29 cannot connect. A build without the liveness ping is declared dead by a new build after 75 s idle.
- **Nothing here has run on a phone, and nothing has had an independent cryptography review.**

Fixed in that review, in code: ratchet desync when both sides send at once; sessions that failed forever while shown as live; the APK receive with no overall deadline; low-order X25519 keys; user text in crash reports; the old core not wiped on identity deletion; read receipts and last-seen state surviving a removed contact; the handshake's lack of forward secrecy against later theft of the responder's keys; undetected half-open links.
